# ErisStepper

One stepper axis behind a **TMC2209**: STEP/DIR for motion, UART for
configuration and diagnostics, and a deliberately small G-code surface (`G0`)
on top of the normal Eris command set.

The split is the point of the flavor. STEP/DIR is a pair of wires that say
*"advance one microstep, this way"* — fast, dumb, and the only thing the motor
timing depends on. The UART says what a microstep *means*: how much current the
coil gets, how many microsteps make a full step, which chopper mode runs, and
whether the driver is in thermal shutdown. A TMC2209 works with STEP/DIR alone;
wiring the UART is what turns it from a stepper driver into an instrument you
can query -- including asking it whether the axis has run into something
(see [Hard-stop detection](#hard-stop-detection)).

## Status

🟡 Compile-verified on Teensy 3.6 (ChibiOS), Seeeduino XIAO / SAMD21 (FreeRTOS)
and ESP32 (ESP-IDF FreeRTOS, core 3.3.11). Bringing it up on SAMD21 exposed
three bugs in `eriscommon` itself, all fixed (see
[Troubleshooting](#troubleshooting) and `lessons_learned.md` 18-20). Still not
verified moving a motor.

## Hardware

- **Target board:** any Eris-supported board. Nothing here is board-specific —
  motion is generated by an ordinary RTOS thread, not a hardware timer.
- **Driver:** TMC2209 breakout (BigTreeTech, Watterott SilentStepStick, FYSETC)
- **Motor:** any bipolar stepper the driver can run (NEMA 11/14/17)
- **Motor supply:** 12–24 V, separate from the MCU, grounds tied together

### Wiring

| TMC2209 | MCU (Teensy / SAMD default) | ESP32 default |
|---|---|---|
| `STEP` | `2` | `25` |
| `DIR` | `3` | `26` |
| `EN` | `4` | `27` |
| `DIAG` | `5` (optional, `TMC_USE_DIAG 1`) | `5` |
| `PDN_UART` | `Serial1 TX` via **1 kΩ**, and `Serial1 RX` direct | `Serial2` (TX 17 via 1 kΩ, RX 16) |
| `VM` / `GND` | motor supply, 12–24 V | |
| `VIO` | 3V3 (5 V on a 5 V board) | |
| `M1A M1B M2A M2B` | one motor coil per pair | |

The single-wire UART needs the series resistor:

```
  MCU TX --[1k]--> PDN_UART
  MCU RX ----------+
```

The TMC2209 has one pin for both directions. The resistor lets the driver pull
the line low to answer while the MCU's idle-high TX is still driving it. Without
it the MCU wins every arbitration and you get reads that time out while writes
appear to work — `TMC::begin()` calls that out specifically by checking `IFCNT`.

The MCU also hears its own transmission echoed back. `tmc2209.cpp` resyncs on
the `0x05 0xFF` reply header rather than discarding a fixed number of bytes, so
it works whether or not the echo is there.

**⚠ Never unplug the motor with the driver powered.** The TMC2209 will survive
most abuse, but not that one.

## Pin and axis configuration

Everything lives in `configuration.h`. The values worth checking before the
first run:

| Macro | Default | What it is |
|---|---|---|
| `TMC_RSENSE` | `0.11f` | **Sense resistor on YOUR board.** Wrong value ⇒ wrong current. |
| `TMC_RMS_CURRENT_MA` | `600` | Motor RMS current. Start low. |
| `TMC_MICROSTEPS` | `16` | Set over UART; overrides MS1/MS2. |
| `TMC_STEALTHCHOP` | `1` | 1 = quiet StealthChop, 0 = SpreadCycle. |
| `TMC_ADDRESS` | `0` | Set by MS1/MS2 on the board. |
| `STEPPER_STEPS_PER_MM` | `80.0f` | 200 full steps × 16 µsteps ÷ 40 mm/rev (GT2-20T). |
| `STEPPER_DEFAULT_FEED` | `600.0f` | mm/**min**, the G-code `F` convention. |
| `STEPPER_MAX_FEED` | `3000.0f` | mm/min. |
| `STEPPER_ACCEL` | `500.0f` | mm/s². |
| `STEPPER_MIN_POS_MM` / `MAX` | `±200.0f` | Soft limits (`STEPPER_SOFT_LIMITS 0` to disable). |
| `STEPPER_INVERT_DIR` | `0` | Flip travel direction without rewiring. |
| `STEPPER_STALL_DETECT` | `1` | Hard-stop detection on/off. |
| `TMC_SGTHRS` | `60` | Stall threshold, 0..255. **Higher trips earlier.** Must be tuned. |
| `TMC_USE_DIAG` | `0` | 1 if the DIAG pin is wired (instant detection). |
| `STEPPER_STALL_HALT` | `1` | 1 = stop on stall, 0 = report only. |

There is **no homing and no limit switch**. Position `0 mm` is wherever the axis
sat at power-up, or wherever `ZERO` was last issued. The soft limits are
relative to that, so they protect against a typo, not against a crash.

## Commands

The universal Eris set (`INFO`, `S_F`, `S_ON`, `S_OFF`, `S_MODE`, `DESC`,
`S_TIME`, `KILL`, `START`, …) applies. On top of it:

### G-code

| Command | Effect |
|---|---|
| `G0 X<mm>` | Move to an absolute position at the current feedrate |
| `G0 X<mm> F<mm/min>` | Set the feedrate, then move at it |
| `G0 F<mm/min>` | Set the feedrate only — nothing moves |
| `G0` | Report `X: TGT: F: V:` and whether the axis is moving |

Absolute millimetres (G90 semantics — there is no G91), and `F` is millimetres
per **minute**, as on any G-code controller. The feedrate persists until
changed. Words are space-separated (`G0 X10 F600`); `G0X10` will not parse,
because Eris tokenizes on whitespace before the parser sees the line. A bare
letter with a separate value (`G0 X 10`) also works, for typing by hand.

`G1` is deliberately **not** implemented. On a single axis with no extruder it
would be a synonym for `G0`, and a silent synonym is worse than an unknown
command: a sender emitting `G1` expects coordinated multi-axis feed moves, which
this is not. An unsupported word (`Y`, `Z`, `E`, `S`…) is reported and moves
nothing rather than being ignored.

### Native

| Command | Effect |
|---|---|
| `STEP` | Dump buffered telemetry as text (`position:velocity:sg`) |
| `TMC` | Driver status: link, version, `DRV_STATUS` decoded |
| `TMC I <mA>` | Set motor RMS current, live |
| `TMC U <n>` | Set microsteps (1…256, power of two), live |
| `TMC S <0\|1>` | SpreadCycle / StealthChop, live |
| `SG` | Report live StallGuard reading, threshold, armed/stalled state |
| `SG <0..255>` | Retune the stall threshold, live |
| `SG CLR` | Clear the stall latch |
| `EN <0\|1>` | Release / energize the motor |
| `ZERO` | Call the current position 0 mm |
| `STOP` | Decelerate to a halt and cancel the move |

`TMC I/U/S` are the reason the UART is worth wiring: none of them is reachable
on a standalone driver without a screwdriver on the VREF trimpot and a jumper
change. Note that `TMC U` changes what one step is worth while
`STEPPER_STEPS_PER_MM` keeps describing the old one — the command says so.

`EN 0` releases the motor, which means it can be back-driven, which means the
step count no longer describes the machine. The firmware therefore cancels the
pending move as well; re-issue `ZERO` and `G0` after re-enabling.

## Streaming

One feature, `STEP`:

```
S_F STEP
S_ON
```

It boots with `S_F STEP` already selected in ASCII mode
(`SerialCom::bootDefaults("STEP", true)` in the `.ino`), so plugging the board
in and opening the **Arduino Serial Plotter** shows position, velocity and
target immediately, with no typing. The Python driver sends `S_MODE BIN` on
connect to switch to the binary protocol.

`StepperSample_t` (24 bytes, described with `ERIS_DESCRIBE_*`, so `DESC` reports
it and the Python driver needs no `format=` string):

| Field | Type | Role | Unit |
|---|---|---|---|
| `timestamp` | f32 | time | ms since t0 |
| `position` | f32 | signal | mm |
| `velocity` | f32 | signal | mm/s, signed |
| `target` | f32 | signal | mm |
| `sg` | u16 | signal | StallGuard4 `SG_RESULT`, 0...1023 |
| `status` | u16 | meta | packed `DRV_STATUS`, see `tmc2209.h` |
| `moving` | u8 | meta | 0/1 |
| `enabled` | u8 | meta | 0/1 |
| `stalled` | u8 | meta | 0/1, latched hard-stop flag |
| `pad` | pad | - | keeps `sizeof` at 24 with no implicit padding |

The three floats are the traces you want when tuning a move, and `sg` is the one
you want when tuning the stall threshold, so all four are `SIGNAL` and the
Serial Plotter draws them. Note that `sg` (0...1023) will dominate the autoscale
next to a position in millimetres -- that is the right trade while tuning, and
the flags stay `META` so they never join in.

```python
from eris import Eris
dev = Eris(['STEP'], port='COM3')     # no format= needed: DESC supplies it
dev.startStreaming()
```

## Hard-stop detection

**This is not a current threshold, and it cannot be.** A chopper driver
regulates coil current to a constant, so driving the axis into a hard stop does
not make the current rise -- it was already at `IRUN`. Watching current would
detect nothing at all. That is also why steppers lose steps *silently*.

What the TMC2209 offers instead is **StallGuard4**, and it measures the same
physical thing a current threshold would be reaching for, from the right place:
the driver derives the motor load angle from its own back-EMF and reports it as
`SG_RESULT`, 0...1023.

- `SG_RESULT` is **high** when the motor spins freely.
- It **falls** as mechanical load rises.
- It approaches zero as the rotor is about to lose sync -- which is what hitting
  a hard stop is.

The driver calls it a stall when `SG_RESULT <= 2 * SGTHRS`. So `TMC_SGTHRS` is
**inverted relative to intuition: a higher value trips earlier.**

### The two detection paths

| | How | Latency | Cost |
|---|---|---|---|
| `TMC_USE_DIAG 1` | Driver raises `DIAG`; the motion thread reads the pin each tick | <= 1 ms | a `digitalRead` |
| `TMC_USE_DIAG 0` (default) | Telemetry thread polls `SG_RESULT` over UART | <= 20 ms (`STEPPER_SG_DIVIDER 2` -> 50 Hz) | one UART round trip per poll |

Wire `DIAG` if you care how far the axis travels past what it hit. At the
default 600 mm/min, 20 ms of polling latency is 0.2 mm of extra travel; at 1 ms
it is 0.01 mm.

Either way the UART work stays off the 1 ms motion thread, which cannot afford a
~1 ms transaction. The motion thread only ever reads a pin and sets a flag; the
telemetry thread does the polling and all of the reporting.

### The two gates

A low reading is not believed unless both are satisfied:

1. **Speed** -- `SG_RESULT` needs back-EMF to measure. Below
   `STEPPER_STALL_MIN_FEED` (60 mm/min) it is noise.
2. **Time** -- `STEPPER_STALL_ARM_MS` (150 ms) after the move starts. The load
   angle is still settling during the acceleration ramp, so an unarmed detector
   trips on every move it begins.

Without both, the axis stalls on itself immediately and the feature is useless.
`SG` reports whether the detector is armed right now.

### What happens on a stall

With `STEPPER_STALL_HALT 1` (default) the axis **stops dead** -- no deceleration
ramp. The usual reason to ramp down is to avoid losing steps, but the axis is
already against something and the steps are already lost; a ramp would only add
distance travelled into whatever we hit.

Then `stalled` goes to 1 in the stream and an `ERROR` packet is emitted naming
the position and the readings. Because `DIAG` also fires on driver faults, the
report reads `DRV_STATUS` first and says whether this was a mechanical stall or
a thermal/short fault -- very different problems.

The latch clears on the next `G0` (usually the move that backs the axis off what
it hit), on `ZERO`, on `EN 1`, or explicitly with `SG CLR`. It deliberately does
**not** block motion while set: a detector that leaves the machine jammed
against an obstacle is worse than no detector.

With `STEPPER_STALL_HALT 0` nothing stops; `stalled` and the error still appear
in the stream. Useful when you want to log where the axis is loaded without the
firmware acting on it.

### Tuning the threshold

There is no universal `SGTHRS`. It depends on the motor, the current, the speed
and the mechanics, and it has to be tuned per machine:

```
SG                 # read it while the axis is idle
G0 F600            # pick the speed you will actually run at
G0 X50             # start a long move
SG                 # read it while running free -- say it reads 420
SG 150             # threshold a bit under half of that (420/2 = 210)
```

Then push on the axis by hand: the reading should dive, and it should trip
before the motor audibly loses steps. Raise `SGTHRS` if it misses real stalls,
lower it if it trips on normal load. Streaming (`S_F STEP`, Serial Plotter) is
far easier than polling `SG` by hand -- the `sg` trace is there for exactly this.

Re-tune after changing current, speed or microstepping. StallGuard is
speed-dependent: a threshold tuned at 600 mm/min will not hold at 3000.

### Requirements and limits

- **StealthChop only.** StallGuard4 is specified for StealthChop; with
  `TMC_STEALTHCHOP 0` the readings are noise. `TMC::begin()` warns at boot if
  you configure that combination.
- **`TCOOLTHRS` must be set** or `SG_RESULT` stays at 0 forever, which looks
  exactly like a permanently stalled motor. `TMC::begin()` writes it.
- **The UART must be up.** No UART means no `SGTHRS` and no `SG_RESULT`, and on
  a failed read the detector skips that sample rather than treating the missing
  value as a low one -- a dropped datagram must never slam the axis to a halt.
- This is sensorless and approximate. It finds a hard stop; it is not a
  substitute for a limit switch on a machine where overtravel does damage.

Sensorless homing is the obvious thing to build on this -- move toward the stop
at a low feed, wait for `stalled`, `ZERO`, back off -- but it is not implemented
here; there is no `G28`.

## How motion is generated

A stepper wants step edges at microsecond precision; an RTOS thread wakes on a
millisecond tick. The usual answer is a hardware timer ISR — but that is a
different peripheral on every board Eris supports, and it is exactly what made
the old ErisMPU board-specific.

So this keeps the RTOS in charge of *when* and gives up only on the spacing
*within* a tick. Each 1 ms tick the motion thread computes how many steps the
current velocity owes it, emits them as one burst, and carries the fractional
remainder into the next tick — so the average rate is exact even at rates that
are not a whole number of steps per tick. At 16 microsteps the bunching is well
inside what the rotor filters out, and the driver's own `multistep_filt` smooths
it further.

The cost is a ceiling: `STEPPER_MAX_STEPS_PER_TICK` (32) steps per 1 ms tick, so
**32 000 steps/s**, which at the default 80 steps/mm is 400 mm/s. `setFeed()`
clamps to it rather than letting a feedrate quietly not be reached. The burst
also holds the CPU for 32 × 2 × 3 µs ≈ 200 µs of each millisecond, at
`ERIS_NORMAL_PRIORITY + 2` — above the sensors, below nothing else that matters.

Velocity follows a trapezoidal ramp: accelerate at `STEPPER_ACCEL`, cruise at
the feedrate, start decelerating once the remaining distance is down to
`v²/2a`. Commanding a stepper straight to speed from standstill does not move it
faster, it stalls it.

A new target on the other side of the axis, or a `STOP`, sheds speed along the
current direction first and flips only once the axis is slow enough to stop.
Slamming `DIR` over at speed loses steps, and lost steps are invisible: the
reported position would quietly stop matching the machine.

## Troubleshooting

**It prints `HELLO, This is Eris` and then nothing.** This was a bug in
`eriscommon`, not in the flavor, and it is fixed -- make sure your `eriscommon`
is current. On SAMD FreeRTOS, `start()` used to run before
`vTaskStartScheduler()`, and on that port a critical section taken before the
scheduler masks interrupts *and never unmasks them* -- which `xTaskCreate()`
does internally, so `Heartbeat::start()` on line one of `start()` killed
interrupts for the rest of it. `millis()` then stops advancing and
`TMC::begin()`'s `delay(10)` never returns. `start()` now runs in its own
bootstrap task with the scheduler up. See `lessons_learned.md` section 18.

A flavor-side corollary that still applies: anything `start()` reaches runs at
`ERIS_NORMAL_PRIORITY + 3`, so keep device bring-up bounded -- a driver that
never answers should time out, not retry forever.

**`ASSERT: uxQueueMessagesWaiting :#1985`.** The queue handle is `NULL`: a
streaming feature is selected whose buffer was never `init()`ed. `init()` runs
inside the sensor's `start()`, so this is what you get if `Stepper::start()` is
commented out while `bootDefaults("STEP", ...)` still asks for the feature.
`ErisBuffer` now guards on its `ready` flag and streams nothing instead of
asserting, but the fix is to start the thread. See section 20.

**`ASSERT:` from `vTaskDelayUntil`, or a thread that never runs again.** Fixed
in `eris_rtos.h` -- `eris_sleep_until()` was passing a remaining-time where
FreeRTOS wanted a period, which asserts on 0 and underflows when late. A 1 ms
thread hits it immediately. See section 19; make sure your `eriscommon` is
current.

**The board locks up under load.** The motion thread runs at
`ERIS_NORMAL_PRIORITY + 2`. If a tick's work ever overruns `STEPPER_TICK_MS` it
must not try to catch up, or it spins forever above every other thread --
`paceTick()` resyncs instead, trading step rate for staying alive. If you raise
`STEPPER_MAX_STEPS_PER_TICK` on a slow board, that is the budget you are
spending.

## Dependencies

- `eriscommon`
- ChRt (Teensy) or Arduino FreeRTOS (SAMD21 / nRF52) — auto-selected
- `SerialCommand`, `PacketSerial`

No TMC library. `tmc2209.cpp` is a ~300-line implementation of the three
datagram shapes the datasheet defines, with the registers this flavor actually
uses — worth reading once, and it keeps the flavor compiling with nothing
installed.

The header is `serialcommand**s**.h`, plural, on purpose: Windows filesystems
are case-insensitive, so a local `serialcommand.h` gets found by eriscommon's
`#include <SerialCommand.h>` and shadows the library header. See
`lessons_learned.md` §5 — this flavor hit it on the ESP32 build.

## Bring-up checklist

1. Set `TMC_RSENSE` for your breakout and `TMC_RMS_CURRENT_MA` low (400–600 mA).
2. Upload, open the Serial Monitor at 115200. Expect
   `TMC2209 ready: 600 mA rms, 16 microsteps, StealthChop`.
   If you get `TMC2209 UART not answering`, fix the wiring before anything else
   — the driver will still step, using MS1/MS2 and the VREF pot, which is not
   what the configuration says.
3. `TMC` — confirm `version:0x21` and `standstill`.
4. `G0 F300` then `G0 X10`. The axis should move 10 mm and report `ok`.
5. Check `STEPPER_STEPS_PER_MM` against what actually moved, and correct it.
6. Raise the current until the motor has the torque you need and no more; check
   `TMC` for `OTPW` after a few minutes of work.
7. Tune the stall threshold -- see [Hard-stop detection](#hard-stop-detection).
   Until you do, `TMC_SGTHRS 60` is a placeholder, not a working setting: it
   will either never trip or trip on every move.
